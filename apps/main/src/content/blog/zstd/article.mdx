# zstd（Zstandard）でHTTPのレスポンスを圧縮する

<BrowserSupportStatus featureId="zstd" />

## はじめに

`zstd`（Zstandard）は、Metaが開発した可逆圧縮のアルゴリズムです。HTTPではレスポンスの圧縮形式の1つとして使え、ブラウザは`Content-Encoding: zstd`で返されたレスポンスを展開します。

`gzip`と`Brotli`で返せていれば、多くの場面はそれで足ります。`zstd`を足して変わるのは、圧縮と展開にかかる時間です。リクエストのたびに圧縮するレスポンスを、`gzip`より短い時間で小さくしたいときに向いています。

レスポンスボディは、`Accept-Encoding`リクエストヘッダーと`Content-Encoding`レスポンスヘッダーを使って圧縮できます。

### Accept-Encoding

`Accept-Encoding`はリクエストヘッダーで、クライアントが対応している圧縮形式をサーバーに伝えます。

```http
Accept-Encoding: gzip, deflate, br
```

カンマ区切りで複数の圧縮形式を指定できます。また、`q`パラメータで各形式の優先度（0〜1）を指定することもできます。

```http
Accept-Encoding: gzip;q=0.8, br;q=1.0
```

優先度を指定しない場合は`1.0`として扱われます。`q=0`は、その形式を受け入れないという意味です。

### Content-Encoding

`Content-Encoding`はレスポンスヘッダーで、サーバーが実際に適用した圧縮形式をクライアントに伝えます。

```http
Content-Encoding: br
```

クライアントはこのヘッダーを見て、適切な方法でレスポンスボディを展開します。

なお、サーバーが圧縮に対応していない場合や、クライアントが送った`Accept-Encoding`の中に対応形式がなかった場合は、`Content-Encoding`ヘッダーなしで非圧縮のまま返されます。

`identity;q=0`等で非圧縮も明示的に拒否している場合、サーバーは`406 Not Acceptable`を返せます。ただし、返すかどうかはサーバーが決め、`Accept-Encoding`を無視して非圧縮で返すこともできます。このサイトに2026年11月に`curl`で`Accept-Encoding: identity;q=0`を送ると、`200`で非圧縮のまま返りました。

`zstd`はこの仕組みに乗っかる形で、Baseline 2026で新たに加わった圧縮形式です。

## zstd

`zstd`は[RFC 8878](https://www.rfc-editor.org/rfc/rfc8878)で標準化されていて、`zlib`レベルの圧縮率を保ちつつリアルタイム圧縮が可能なことを目標に設計されています。

[ベンチマーク](https://github.com/facebook/zstd?tab=readme-ov-file#benchmarks)によれば、`gzip(zlib)`を上回る圧縮率を誇り、`Brotli`と同等のサイズを維持しながら、数倍速い展開速度を実現しています。
これにより、クライアント側のCPU負荷を抑えつつ高速なページロードが可能です。

また、圧縮速度と圧縮率はトレードオフの関係にありますが、圧縮レベルを細かく調整することでそのバランスを柔軟に変えられます。

手元のNode.js 26.13.0（zstd 1.5.7）で、この記事のHTML（約211KB）を圧縮して比べました。`gzip`（レベル6）は1.5msで52KB、`zstd`（既定のレベル3）は0.2msで37KBになり、`zstd`の方が速く小さくなりました。最も小さくなったのは、123msかけた`Brotli`（品質11）の28KBです。react-domの本番用のJS（約625KB）では、レベル3の`zstd`は`gzip`より大きくなり、レベル9で`gzip`より速く小さくなりました。展開は、どちらのファイルでも`zstd`が最も速く終わりました。

### ブラウザでの利用

Baseline 2026に加わったことで、主要なブラウザで`zstd`が利用できるようになりました。
対応したブラウザでは、`Accept-Encoding`ヘッダーに`zstd`が自動的に追加されます。

```http
Accept-Encoding: gzip, deflate, br, zstd
```

サーバーが`zstd`圧縮に対応している場合、`Content-Encoding: zstd`ヘッダーとともにzstd圧縮されたレスポンスを返します。

```http
Content-Encoding: zstd
```

Node.js 26.13.0では、`node:zlib`の`zstdCompressSync`で圧縮して返せます。次のコードを`server.mjs`として保存し、`node server.mjs`で起動します。

```js title="server.mjs"
import { createServer } from 'node:http';
import { zstdCompressSync } from 'node:zlib';

createServer((req, res) => {
  const acceptEncoding = req.headers['accept-encoding'] ?? '';
  console.log(acceptEncoding);
  const body = Buffer.from('<h1>Hello, zstd!</h1>');
  if (acceptEncoding.includes('zstd')) {
    res.writeHead(200, {
      'Content-Type': 'text/html; charset=utf-8',
      'Content-Encoding': 'zstd',
      Vary: 'Accept-Encoding',
    });
    res.end(zstdCompressSync(body));
    return;
  }
  res.writeHead(200, {
    'Content-Type': 'text/html; charset=utf-8',
    Vary: 'Accept-Encoding',
  });
  res.end(body);
}).listen(3000);
```

Chrome 156かFirefox 159で`http://localhost:3000`を開くと、ターミナルに`gzip, deflate, br, zstd`と出て、`zstd`で圧縮した見出しが表示されます。Safari 27.2では`gzip, deflate`とだけ出て、圧縮していない見出しが表示されます。Safari 27.2は`zstd`で返したレスポンスも展開できますが、`http`の`localhost`へのリクエストには`zstd`を付けませんでした。

ただし、ブラウザが`zstd`を送っても、サーバーが`zstd`を選ぶとは限りません。このサイトはVercelで配信していますが、2026年11月に`curl`で`Accept-Encoding: gzip, deflate, br, zstd`を送ると`Content-Encoding: br`が返り、`zstd`だけを送ると圧縮されずに返りました。どの形式で返すかはサーバーやCDNが決めるので、`zstd`で配信したいときは、DevToolsのネットワークパネルで`Content-Encoding`を見て、配信側が対応しているかを確かめます。

### 圧縮辞書転送

<BrowserSupportStatus featureId="compression-dictionary-transport" />

`zstd`はさらに、圧縮辞書を用いた圧縮辞書転送（[RFC 9842](https://www.rfc-editor.org/rfc/rfc9842)）にも対応しています。
通常の圧縮はレスポンス内の冗長性を検出して圧縮しますが、圧縮辞書転送ではあらかじめ用意した辞書を参照することで、さらに効率的な圧縮が可能です。

たとえば、ライブラリの旧バージョンを辞書として使うと、新バージョンとの差分だけを圧縮して転送できるため、転送サイズを大幅に削減できます。
辞書圧縮が利用可能な場合は`Accept-Encoding`に`dcz`（dictionary-compressed Zstandard）が追加されます。

```http
Accept-Encoding: gzip, deflate, br, zstd, dcb, dcz
Available-Dictionary: :pZGm1Av0IEBKARczz7exkNYsZb8LzaMrV7J32a2fFG4=:
```

`Available-Dictionary`は保持している辞書の識別子を伝えます。`dcz`の他に`dcb`（dictionary-compressed Brotli）もあります。

辞書にするレスポンスには、`Use-As-Dictionary: match="/data*"`のように、その辞書を使うURLのパターンを付けます。手元で試すと、Chrome 156はこのレスポンスを受け取ったあと、`/data`で始まるURLへのリクエストに`dcb, dcz`と`Available-Dictionary`を付けました。Safari 27.2と、既定の設定のFirefox 159は付けませんでした。圧縮辞書転送は、まだBaselineに達していません。

## おわりに

`zstd`がBaseline 2026で追加され、`gzip`・`Brotli`に並ぶ圧縮形式の選択肢として使えるようになりました。

対応したブラウザは`Accept-Encoding`に`zstd`を自動で付けるので、サーバーかCDNが`zstd`で返せば使われます。事前に圧縮して置ける静的なファイルは時間をかけた`Brotli`が最も小さくなり、リクエストのたびに圧縮するレスポンスは`zstd`で`gzip`より速く小さくできます。配信している`Content-Encoding`を確かめて、`zstd`への対応を検討してみてください。
