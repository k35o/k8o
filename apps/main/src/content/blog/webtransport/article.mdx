# WebTransportでQUIC（HTTP/3）の双方向通信をする

<BrowserSupportStatus featureId="webtransport" />

## はじめに

WebTransportは、QUIC（HTTP/3）の上で、ブラウザとサーバーがデータを双方向にやり取りするAPIです。1本の接続に独立したストリームをいくつも開け、届かなくても再送しないデータグラムも送れます。

チャットや通知のように少量のテキストをやり取りするだけなら、これまでどおりWebSocketで足ります。WebSocketはTCPの上で1本のメッセージ列しか持てないので、一部のデータが遅れると後のデータまで待たされます。遅れたデータを待たずにほかの流れを進めたい通信や、ゲームの座標のように古い値を捨ててよい通信は、WebTransportで書けます。

Baseline 2026で主要ブラウザすべてで利用可能になりました。

## WebTransportとは

HTTP/3はTCPではなくUDP上に作られたQUICというプロトコルを使っており、WebTransportはこのQUICの特徴をそのままWebに持ち込みます。

具体的には以下のような特徴があります。

- 複数ストリーム: 1つのコネクション上に独立したストリームを何本でも開ける
- 双方向／単方向ストリーム: 用途に応じて選べる
- データグラム: 順序保証も再送もない、軽量な送受信ができる
- 常にHTTPS: `crypto.randomUUID()`などと同様、Secure Contextでのみ動作する
- ネットワーク切り替えに比較的強い: QUICのコネクションマイグレーションにより、Wi-Fiからモバイル回線に切り替わったときもTCPベースよりコネクションを維持しやすい

### WebSocketとの違い

WebSocketと比較すると、WebTransportには次のような違いがあります。

- プロトコル: WebSocketはTCP上で動くのに対し、WebTransportはHTTP/3（QUIC、UDP）上で動く
- ストリームの本数: WebSocketは順序付き・信頼性のある単一のメッセージ列として扱われ独立したストリームを持てないが、WebTransportは1つのコネクション上に複数本の独立したストリームを開ける
- Head-of-Line Blocking: WebSocketでは発生するが、WebTransportではストリームごとに独立しているため発生しない
- 信頼性のない高速送信: WebSocketにはないが、WebTransportはデータグラムで実現できる
- ネットワーク切り替え: WebSocketはコネクションが切れてしまうが、WebTransportはQUICのコネクションマイグレーションにより維持できる場合がある

とはいえWebSocketを完全に置き換えるものではありません。WebSocketはテキストメッセージをそのまま送受信でき、サーバー側のライブラリやホスティング環境も成熟しているため、チャットや通知のように少量のテキストをやり取りするだけの用途では、今でもWebSocketの方が手軽です。

一方で、低遅延で大量のデータをやり取りするユースケース（ゲーム、ライブ配信、リアルタイムコラボレーションなど）では、WebTransportの複数ストリームやデータグラムが大きな利点になります。

## 使い方

WebTransportに渡すURLは`https`で始めます。`http`のURLや`#`の付いたURLを渡すと、コンストラクタが`SyntaxError`を投げます。ポート番号を省くと、`https`の既定の443番につなぎます。Web Workerからも利用できます。

### コネクションを開く

`WebTransport`コンストラクタにURLを渡し、`ready`プロミスを待つことで接続が確立します。

```ts
const transport = new WebTransport('https://example.com:4433/chat');

await transport.ready;
console.log('接続完了');

// 切断時の処理
transport.closed
  .then(() => console.log('正常に切断されました'))
  .catch((err) => console.error('切断時にエラー', err));
```

切断したいときは`transport.close()`を呼びます。

手元のサーバーに開発用の自己署名の証明書でつなぐときは、`serverCertificateHashes`に証明書のSHA-256のハッシュを渡します。

```ts
const transport = new WebTransport('https://localhost:4433/chat', {
  serverCertificateHashes: [{ algorithm: 'sha-256', value: certHash }],
});
```

`certHash`は、`openssl x509 -in cert.pem -outform der | openssl dgst -sha256 -binary`で出る32バイトを`Uint8Array`にしたものです。仕様では、ハッシュで許す証明書はECDSAの鍵で、有効期間が2週間以内のものに限られます。

手元では、Deno 2.9.8の`Deno.upgradeWebTransport`で立てたエコーのサーバーに、P-256の鍵で有効期間10日の証明書を使ってつなぎました。Chrome 156、Safari 27.2、Firefox 159のどれでもこの方法でつながり、データグラムと双方向ストリームが往復しました。`serverCertificateHashes`を渡さないと、どれも`ready`が`WebTransportError`で拒否されました。

### データグラムの送受信

データグラムは順序保証も再送もない、もっとも軽量な送受信方法です。
最悪届かなくても最新の値で上書きすればよい、チャットの入力状態やキャラクターの座標のようなデータの送受信に向いています。

データグラムは`transport.datagrams`の`readable`で受け取り、`createWritable()`で作った書き込み用のストリームで送ります。Chrome 156は`createWritable()`を持たず、`writable`だけを持ちます。Safari 27.2は逆に`writable`を持たないので、`transport.datagrams.writable.getWriter()`と書くと`TypeError`になりました（Firefox 159は両方を持つ）。どちらも標準のStreams APIなので、`getReader()`や`getWriter()`でそのまま扱えます。

```js
// 送信
const writable =
  transport.datagrams.createWritable?.() ?? transport.datagrams.writable;
const writer = writable.getWriter();
await writer.write(new Uint8Array([1, 2, 3]));
writer.releaseLock();

// 受信
const reader = transport.datagrams.readable.getReader();
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  console.log('受信:', value);
}
```

1つのデータグラムで送れる大きさは`transport.datagrams.maxDatagramSize`で分かります。手元のサーバーにつなぐと、Chrome 156は1211、Firefox 159は1024、Safari 27.2は65535を返しました。

### 単方向ストリーム

ストリームはデータグラムと違い、順序が保証され、欠損した場合は再送されます。
クライアントから一方向にデータを送るだけでよい場合は単方向ストリームが便利です（Unidirectionalは「単方向の」という意味）。

```ts
const stream = await transport.createUnidirectionalStream();
const writer = stream.getWriter();
await writer.write(new Uint8Array([10, 20, 30]));
await writer.close();
```

サーバー側から送られてくる単方向ストリームは`transport.incomingUnidirectionalStreams`から受け取れます。

```ts
const reader = transport.incomingUnidirectionalStreams.getReader();
while (true) {
  const { value: stream, done } = await reader.read();
  if (done) break;
  // stream は ReadableStream
  const streamReader = stream.getReader();
  // ...読み込み処理
}
```

### 双方向ストリーム

リクエスト・レスポンスのように、両方向にデータをやり取りしたいときは双方向ストリームを使います（Bidirectionalは「双方向の」という意味）。
1つの`WebTransportBidirectionalStream`が`readable`と`writable`の両方を持っています。

送信と受信は独立しているので、次のように並行して動かせます。送信の完了を待たずに受信ループを回せるので、サーバーから届くデータをリアルタイムに処理できます。

```ts
// [!og]
const stream = await transport.createBidirectionalStream();

// 受信ループを先に起動しておく
const receiveTask = (async () => {
  const reader = stream.readable.getReader();
  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    console.log('受信:', value);
  }
})();

// 受信ループの裏で送信する
const writer = stream.writable.getWriter();
await writer.write(new Uint8Array([1, 2, 3]));
await writer.close();

await receiveTask;
```

複数のストリームを並行して開けるので、たとえばファイル転送と制御メッセージを別々のストリームで流す、といった設計が自然に書けます。

## おわりに

WebTransportを簡単に紹介しました。

HTTP/3の特徴をそのままWebに持ち込んだAPIで、複数ストリームの並行処理や、データグラムによる軽量な送信、ネットワーク切り替え時にも維持しやすい接続といった、WebSocketでは難しかった通信が実現できます。
とはいえWebSocketの手軽さや成熟したエコシステムには今も大きな魅力があるので、用途に応じて使い分けるのが現実的です。

Baseline 2026で主要ブラウザすべてで使えるようになったので、ピッタリな状況があればぜひ使ってみてください。
