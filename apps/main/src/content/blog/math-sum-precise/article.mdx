# Math.sumPreciseで配列の合計の丸め誤差を抑える

<BrowserSupportStatus featureId="math-sum-precise" />

## はじめに

`Math.sumPrecise()`は、数値の配列などを受け取り、その合計を返す静的メソッドです。`+`のように足すたびに丸めるのではなく、すべての値を正確に足した結果を最後に1回だけ丸めるので、足す順序で結果が変わりません。Chrome 147が対応して、Baseline 2026に入りました。

JavaScriptの数値はIEEE 754の倍精度浮動小数点数（64bit、仮数部フィールドは52bit、隠れビットを含めて有効精度は53bit相当）で表現されるため、表現できる精度には限りがあります。`a + b`の結果も64bitに収めるために最も近い表現可能な値へ丸められるため、足し算を繰り返すと中間結果の丸め誤差が積み重なります。特に桁の大きく異なる数値が混ざると、本来0ではない合計が0になるなど、結果が大きくずれることがあります。

合計も含めて`Number.MAX_SAFE_INTEGER`以下の整数を足すだけなら、これまでどおり`reduce`や`for...of`の`+`で誤差は出ません。小数や桁の大きく違う数を足すときに、最後に1回だけ丸めた合計を求められるのが`Math.sumPrecise()`です。

```js
const numbers = Array(10).fill(0.1);
console.log(numbers.reduce((sum, n) => sum + n, 0)); // 0.9999999999999999
console.log(Math.sumPrecise(numbers)); // 1
```

コンソールに貼ると、`reduce`は`0.9999999999999999`を、`Math.sumPrecise()`は`1`を出します。

## reduceで足したときの誤差

これまで配列の合計は、`reduce()`や`for...of`で`+`を使って書いていました。

```js
const numbers = [1e20, 0.1, -1e20];
const sum = numbers.reduce((acc, n) => acc + n, 0);
console.log(sum); // 0
```

期待する答えは`0.1`ですが、結果は`0`になります。これは中間結果である`1e20 + 0.1`が浮動小数点数の精度の限界で丸められて`1e20`になり、その後`1e20 + (-1e20)`で`0`になるためです。

順序を入れ替えて`[1e20, -1e20, 0.1]`にすれば`0.1`になりますが、入力の順序で結果が変わります。要素が多いほど途中の丸めが積み重なります。

## Math.sumPrecise()

`Math.sumPrecise()`は、数値の`iterable`を受け取り、途中で丸めずに合計を返します。仕様はアルゴリズムを決めておらず、すべての値を正確に足してから、最後に1回だけ64bitの浮動小数点数に丸めたときと同じ結果を求めています。

```js
console.log(Math.sumPrecise([1e20, 0.1, -1e20])); // 0.1
console.log(Math.sumPrecise([1, 2, 3])); // 6
```

先ほど`reduce`で`0`になった式も、`Math.sumPrecise()`を使えば期待通りの`0.1`を返します。

Node.js 26では、`Math.sumPrecise`は既定で使えず、`TypeError: Math.sumPrecise is not a function`になります。V8のフラグを付けて`node --js-sum-precise`で起動すると使えます。TypeScript 7も、`lib`を`esnext`にしても型が無く、`Property 'sumPrecise' does not exist on type 'Math'`のエラーになります。型は、グローバルの`.d.ts`に足せば使えます。

```ts title="math-sum-precise.d.ts"
interface Math {
  sumPrecise(items: Iterable<number>): number;
}
```

引数は配列に限らず、`Set`やジェネレータなど`[Symbol.iterator]`を持つオブジェクトであれば渡せます。

```js
// [!og]
function* range(start, end) {
  for (let i = start; i < end; i++) {
    yield i;
  }
}

console.log(Math.sumPrecise(range(1, 101))); // 5050
```

`Math.max()`のような可変長引数ではなく`iterable`を1つ受け取るのは、大きな配列を`Math.sumPrecise(...huge)`のように展開して、スタックがあふれないようにするためです。提案のREADMEは、数万要素を超えると`RangeError`になりやすい、と理由を書いています。

名前が`Math.sum`ではなく`Math.sumPrecise`なのも、READMEに理由があります。`Math.sum`では、ふつうに足すだけのメソッドだと思われやすいので、精度を優先して違う（遅くなりうる）方法で足すことを名前で示しています。

100万個の乱数を合計して比べると、SafariとFirefoxでは`Math.sumPrecise()`の方が`reduce`より遅く、Chromeでは逆に速くなります。

## 引数の挙動

`Math.sumPrecise()`に渡せるのは、数値の`iterable`だけです。`Math.max()`のように文字列を数値に変換することはなく、数値以外の値が入っていると`TypeError`を投げます。数値や`null`のように、引数が`iterable`でないときも`TypeError`です。

```js
Math.sumPrecise([1, 2, '3']); // TypeError（要素が数値でない）
Math.sumPrecise([1, 2, null]); // TypeError（要素が数値でない）
Math.sumPrecise(123); // TypeError（iterableでない）
```

`reduce`では文字列がつながったり`null`が`0`になったりしますが、`Math.sumPrecise()`は数値以外をその場で弾くので、想定外のデータが混ざったことに気づけます。

空のiterableを渡した場合は`-0`が返ります。加法の単位元として`+0`ではなく`-0`が返るのは、`-0 + x`が常に`x`と等しいというIEEE 754の性質に合わせるためです。`-0`だけの配列も`-0`のままですが、`+0`が1つでも混ざると結果は`+0`になります。

```js
console.log(Math.sumPrecise([])); // -0
console.log(Math.sumPrecise([-0, -0, -0])); // -0
console.log(Math.sumPrecise([-0, -0, -0, 0])); // 0
```

`Infinity`や`NaN`が入っているときは、同じ非有限値だけならその値を返し、違う非有限値が混ざると`NaN`を返します。

```js
console.log(Math.sumPrecise([1, Infinity])); // Infinity
console.log(Math.sumPrecise([Infinity, Infinity])); // Infinity
console.log(Math.sumPrecise([Infinity, -Infinity])); // NaN
console.log(Math.sumPrecise([Infinity, NaN])); // NaN
console.log(Math.sumPrecise([1, NaN])); // NaN
```

合計がbinary64で表せる範囲を超えると、ふつうの加算と同じく`Infinity`か`-Infinity`を返します。

```js
console.log(Math.sumPrecise([1e308, 1e308])); // Infinity
console.log(Math.sumPrecise([-1e308, -1e308])); // -Infinity
```

`1e308`は10の308乗で、binary64で表せる最大の値`Number.MAX_VALUE`（約1.8e308）に近い値です。途中の和が表現範囲を超えても、最後の合計が収まれば`Math.sumPrecise()`は正しい値を返します。

```js
console.log([1e308, 1e308, -1e308].reduce((sum, n) => sum + n, 0)); // Infinity
console.log(Math.sumPrecise([1e308, 1e308, -1e308])); // 1e+308
```

## 解消できない精度の限界

`Math.sumPrecise()`が取り除くのは合計時の丸め誤差だけで、入力値そのものが持つ表現誤差までは解消できません。有名な`0.1 + 0.2`の例でも、結果は`0.3`にはなりません。

```js
console.log(Math.sumPrecise([0.1, 0.2])); // 0.30000000000000004
```

これは、そもそも`0.1`と`0.2`が思っている値で格納されていないことが原因です。JavaScriptの数値は2進数の浮動小数点数で表されるので、10進数の`0.1`や`0.2`は2進数では有限桁で表せず、最も近い2進小数に丸められて格納されます。実際に格納されている値を`toPrecision()`で取り出すと、末尾に誤差が見えます。

```js
console.log((0.1).toPrecision(20)); // '0.10000000000000000555'
console.log((0.2).toPrecision(20)); // '0.20000000000000001110'
```

この2つの値を（丸めずに）厳密に足すと`0.30000000000000001665...`になり、64bit浮動小数点数で表現できる最も近い値が`0.30000000000000004`です。つまり`Math.sumPrecise([0.1, 0.2])`は、与えられた2つの値の正確な合計を64bit浮動小数点数に丸めた結果としては、まったく正しい値を返しています。

一方で、各要素も合計値もbinary64で厳密に表せる範囲であれば、`Math.sumPrecise()`の結果は数学的な意味でも厳密です。

```js
console.log(Math.sumPrecise([0.5, 0.25, 0.125])); // 0.875（2進数で厳密に表せる）
console.log(Math.sumPrecise([1, 2, 3, 4, 5])); // 15
```

ただし、各要素が厳密に表現できても合計値の方がbinary64の精度を超える場合は、最後の丸めで誤差が出ます。たとえば`1`と`2 ** -54`はどちらも厳密に表現できますが、その正確な和`1 + 2**-54`はbinary64の有効精度（53bit）を超えるため、結果は最終的に`1`へ丸められます。

10進数で正確な値が要るときは、これまでと同じ方法を使います。

- 金額を扱う場合は、整数で扱って最後に桁を戻す
- 任意精度の10進数が必要な場合は、[decimal.js](https://github.com/MikeMcl/decimal.js)のような10進数ライブラリを使う

## おわりに

`Math.sumPrecise()`を使うと、足す順序や桁の差に左右されずに、すべての値を正確に足してから1回だけ丸めた合計を求められます。`0.1`のような入力の値が持つ誤差までは消えないので、10進数で正確な値が要るときは、整数で計算するか10進数のライブラリを使います。
